# MyTerm 端對端加密跨裝置同步執行計劃

最後更新：2026-08-09

本計劃定義 MyTerm 如何在多台 Mac 之間同步主機、群組與選用的密碼，同時維持純本機模式、Keychain 儲存與端對端加密。

## 1. 產品需求

1. 使用者未登入時，MyTerm 的本機功能必須完全正常。
2. 同步必須由使用者主動啟用，不能因 App 更新而自動上傳資料。
3. 登入只用來辨識同步帳號，不代表已同意同步。
4. 群組、子群組、主機資訊、演算法設定與偵測平台可同步。
5. 同步使用單一開關，預設關閉；一旦啟用，群組、主機與已儲存密碼一起同步。
6. Firebase 只能看到帳號識別、同步必要的索引與密文，不能看到主機名稱、IP、帳號、備註或密碼明文。
7. 下載的密碼解密後寫入目的 Mac 的 Keychain，不建立明文密碼檔。
8. 支援至少 100 台主機與多階層群組。
9. 離線時仍可連線與編輯，恢復網路後再同步。
10. 同步失敗不得破壞本機既有資料，也不得阻止 SSH 使用。

## 2. 第一個正式版本不處理的項目

- Windows、Linux、iPhone 或 iPad 版本。
- 多人共同保管庫、組織權限與主機分享。
- 網頁版終端機。
- 自動偵測或強迫進行 90 天密碼輪替。
- 在 Firebase Functions 或 Cloudflare Worker 解密資料。
- 同步 SSH 私鑰檔；第一版只同步私鑰參照狀態，不上傳私鑰內容。
- 無人值守的帳號救援。失去同步密語與復原金鑰時，伺服器無法代為解密。

## 3. 系統架構

```text
MyTerm 畫面與本機功能
        │
        ├── InventoryStore ── 本機主機／群組檔案
        ├── KeychainStore ─── 本機密碼與同步主金鑰
        └── SyncCoordinator
              ├── SyncBackend 介面
              │     ├── FirebaseSyncBackend
              │     └── FakeSyncBackend（測試）
              ├── CryptoVault
              ├── MutationJournal（本機待上傳佇列）
              └── ConflictResolver

Google Desktop OAuth ───── 系統瀏覽器、PKCE、state、loopback 回呼
Firebase Auth REST ─────── 使用者身分 UID 與短效 ID token
Firestore REST ─────────── 加密紀錄、刪除標記與版本資料
```

`SyncBackend` 必須是獨立介面，避免核心資料模型直接依賴 Firebase。如此可進行離線單元測試，也保留未來更換後端的可能性。

雲端模組採延遲啟用：只有使用者主動登入或已啟用同步時才建立網路請求。App 不依賴 Firebase Apple SDK；Authentication 與 Firestore 都透過官方 REST API，避免要求 Apple Developer 付費憑證。純本機模式不得產生 Firebase 網路流量。

## 4. Firestore 建議資料結構

```text
users/{uid}
  schemaVersion
  createdAt
  updatedAt

users/{uid}/devices/{deviceID}
  deviceName
  publicMetadataVersion
  lastSeenAt

users/{uid}/vault/{recordID}
  recordType          // group、host、password、vaultKeyEnvelope
  ciphertext          // Base64 密文
  nonce               // Base64
  authenticationTag   // Base64 或封裝在密文格式中
  keyVersion
  formatVersion
  revision
  modifiedAt
  modifiedByDeviceID
  deleted             // tombstone 刪除標記
```

規則：

- 每位使用者只能存取 `users/{自己的 uid}` 以下資料。
- `recordType`、版本、時間與裝置 ID 可保持明文，其他業務資料都放在密文中。
- 主機名稱、IP、使用者名稱、群組名稱、備註與密碼不能用作 Firestore 文件路徑。
- `recordID` 使用隨機 UUID，避免從識別碼推測內容。
- 限制單筆密文大小與批次寫入數量。
- 不使用一份巨大 JSON 保存全部主機，避免修改一台主機就重傳所有資料。

## 5. 加密設計檢查點

此部分屬於安全關鍵工作。完成獨立檢查、測試向量與復原演練前，不得啟用正式密碼同步。

### 5.1 金鑰階層

1. 第一台 Mac 使用系統安全亂數產生 256 位元主金鑰 `Master Key`。
2. 主金鑰只以 `ThisDeviceOnly` 屬性存入本機 Keychain，不直接上傳。
3. 每筆資料透過 HKDF 從主金鑰與 `recordID`、`recordType`、`keyVersion` 衍生專用金鑰。
4. 資料使用 CryptoKit `AES.GCM` 加密。
5. 將 UID、record ID、record type、format version、key version 放入 AAD，避免密文被移到錯誤帳號或類型後仍能解密。
6. 每次加密使用新的隨機 nonce，禁止重複使用。
7. 解密失敗只回報資料驗證失敗，不把密文、金鑰或明文寫入紀錄檔。

官方參考：[CryptoKit AES.GCM](https://developer.apple.com/documentation/cryptokit/aes/gcm)。

### 5.2 同步密語與復原金鑰

新裝置必須取得主金鑰，不能只靠 Firebase 登入直接解密。規劃兩種封裝方式：

- 使用者設定同步密語。以 Argon2id 搭配隨機 salt 衍生包裝金鑰，再加密主金鑰。
- 系統另外產生高熵復原金鑰，供忘記同步密語或舊 Mac 遺失時使用。

Firebase 只保存：

- Argon2id 參數與 salt。
- 加密後的主金鑰封套。
- 復原金鑰對應的主金鑰封套。
- 金鑰與格式版本。

Firebase 不保存同步密語、復原金鑰或未加密主金鑰。

CryptoKit 本身沒有 Argon2id。實作前要選擇經過維護、授權相容且可固定版本的函式庫，例如受審查的 libsodium Swift 封裝；不能自行發明密碼雜湊。參考標準：[RFC 9106 Argon2](https://www.rfc-editor.org/rfc/rfc9106/)。

復原金鑰只顯示一次，使用者必須明確確認已保存。不可自動存入 iCloud Drive、剪貼簿紀錄或 Firebase。

### 5.3 金鑰與格式升級

- 每筆紀錄包含 `formatVersion` 與 `keyVersion`。
- 變更同步密語時，優先重新封裝主金鑰，不必立刻重加密所有資料。
- 主金鑰疑似外洩時，建立新版本並逐筆重加密。
- 舊版本在遷移完成前保持唯讀相容。
- 清除舊封套前，必須用第二台乾淨 Mac 驗證新封套可復原。

## 6. 資料分類

| 資料 | 預設同步 | 是否加密 | 本機保存位置 |
|---|---:|---:|---|
| 群組名稱與階層 | 是 | 是 | InventoryStore |
| 主機名稱、位址、連接埠 | 是 | 是 | InventoryStore |
| 預設使用者名稱 | 是 | 是 | InventoryStore |
| 驗證方式與演算法選項 | 是 | 是 | InventoryStore |
| 備註與偵測平台 | 是 | 是 | InventoryStore |
| 主機密碼 | 否，獨立同意 | 是 | Keychain |
| 私鑰密碼 | 第一版否 | 不上傳 | Keychain |
| SSH 私鑰檔案／內容 | 否 | 不上傳 | 使用者檔案系統／Secure Enclave 等 |
| known_hosts | 否 | 不上傳 | MyTerm 本機檔案 |
| 本機 Terminal／Serial 紀錄 | 否 | 不上傳 | 不建立雲端紀錄 |
| 同步主金鑰 | 封裝後同步 | 是 | Keychain；雲端只有封套 |

## 7. 合併、刪除與離線行為

- 每筆主機與群組有穩定 UUID、revision、修改時間與修改裝置。
- 本機修改先立即保存，再寫入 Mutation Journal，背景上傳。
- 網路中斷時 Journal 保留；重啟 App 後可繼續。
- 一般欄位採最後確認上傳者為準。兩端同一筆都在基線後修改時，若 Firebase 文件在最近五分鐘內更新，必須顯示「不更新／更新並同步」；超過五分鐘才可由目前裝置自動建立下一個 revision。
- 群組移動與父子關係要檢查循環與不存在的父群組。
- 刪除使用 tombstone，避免離線舊裝置把已刪除資料重新建立。
- tombstone 保留期先設定 90 天，日後依實際使用調整。
- 密碼紀錄與主機 UUID、使用者名稱和驗證方式綁定；這些資料改變時，不得誤用舊密碼。
- Firestore 離線快取不是唯一佇列，MyTerm 自己仍保存可驗證的本機 Journal。[Firestore 離線資料](https://firebase.google.com/docs/firestore/manage-data/enable-offline)

## 8. 使用者操作流程

### 純本機預設狀態

- 設定頁顯示「帳號與同步：未啟用」。
- 可以建立、編輯、匯入、匯出與連線主機。
- 不要求註冊，也不顯示阻擋操作的同步提示。
- Firebase 不初始化、不登入、不上傳。

### 第一台裝置啟用同步

1. 以系統瀏覽器使用 Google 帳號登入。
2. 顯示要同步的資料種類與端對端加密說明。
3. 使用者設定同步密語。
4. MyTerm 在背景自動建立／還原保管庫、雲端封套、首次合併、主機／群組／密碼同步與基線。
5. 全部回讀驗證成功後，單一同步開關才正式啟用。
6. 新保管庫產生並顯示一次復原金鑰。

### 加入第二台 Mac

1. 使用同一 Google 帳號登入。
2. 輸入同步密語或復原金鑰。
3. 在本機解開主金鑰封套。
4. 驗證並解密主機資料。
5. 個別將解密後的密碼寫入這台 Mac 的 Keychain。
6. 顯示裝置名稱、最後同步時間與匯入筆數。

### 停用同步或登出

提供清楚的選項：

- 登出但保留這台 Mac 的本機資料。
- 登出並移除此裝置的同步金鑰。
- 停止單一同步開關，但保留這台 Mac 的本機主機資料與 Keychain 密碼。
- 刪除雲端保管庫；需要重新驗證，不能只按一次就執行。
- 刪除帳號與雲端保管庫後，本機資料是否保留由使用者明確選擇。

## 10. 必須通過的情境

1. 不登入使用數週，所有本機功能不受影響。
2. 登入但不啟用同步，不產生任何主機資料上傳。
3. 啟用單一同步開關後，第二台 Mac 能取得主機、群組並將密碼解密寫入 Keychain。
4. 停用同步後，本機主機與 Keychain 密碼保留，且不再發出資料同步要求。
5. 第一台離線修改 A、第二台修改 B，恢復網路後兩者都保留。
6. 兩台同時修改同一主機，結果可預期且有衝突提示。
7. 離線刪除主機後重新連線，不會被舊裝置復活。
8. 輸入錯誤同步密語時，不覆蓋本機資料也不洩漏解密細節。
9. Firebase 暫停、額度用完或規則拒絕時，SSH 與本機編輯仍可使用。
10. 更換主機密碼後，所有裝置都不再自動使用舊密碼。
11. 刪除雲端保管庫需要重新驗證且能取消。
12. 100 台主機同步不造成明顯介面延遲或異常讀寫費用。

## 11. 必須暫停發布的安全條件

出現以下任一情況時，不得啟用正式同步或發布密碼同步：

- Firebase Console 或除錯紀錄出現主機／密碼明文。
- 跨 UID Security Rules 測試可讀寫其他使用者資料。
- nonce 可能重複，或 AAD 沒有綁定使用者與紀錄身分。
- 復原流程未在乾淨第二台 Mac 實際成功。
- 登出、刪除帳號或停用同步可能意外刪除本機資料。
- App 在純本機模式仍必須登入或依賴 Firebase。
- 密碼可能寫入檔案、Console、Crash Report、剪貼簿紀錄或 GitHub Actions 輸出。
- 加密相依套件來源、授權或維護狀況無法確認。
