# MyTerm Security Design

[繁體中文](SECURITY.md) | **English**

This source repository contains no maintainer cloud configuration, update URL, signing keys, or user data. Builds without local cloud configuration and an explicit update feed do not use a maintainer-hosted service. Independent distributors must use their own services and preserve signature verification.

## Local secrets

- Google sign-in state, the sync master key, and all host passwords share one local AES-256-GCM encrypted vault.
- macOS Keychain holds only one random root key, using `WhenUnlockedThisDeviceOnly` accessibility. It does not migrate to another device through a backup.
- Vault directories and files are accessible only to the current user, and writes use atomic replacement. The host inventory contains no passwords.
- After launch, the app unlocks the root key once and caches it in the current process. Account settings, sync, SSH, and SFTP share that unlock.
- If the root key is missing or malformed, or the vault authentication tag is damaged, MyTerm stops access and does not overwrite existing ciphertext.
- The app does not copy saved passwords to the clipboard or log terminal output.
- Terminal label highlighting examines only a short prefix of the line being drawn. It does not record, transmit, or separately store terminal contents, or change PTY data, remote commands, or copied text. A label may come from any endpoint or ordinary file; its color does not authenticate the message or reliably indicate command success or safety. Highlighting can be disabled in appearance settings.
- Background-output indicators retain only unread state keyed by Session UUID in process memory. They store no output, commands, bytes, or timestamps and are not written to Logs, host exports, Application Support, Keychain, or cross-device sync. The state disappears when the app exits.
- Recent-connection ordering stores only host UUIDs and successful-authentication times in a separate local `0600` file. It contains no host names, addresses, usernames, passwords, or connection contents and is excluded from exports and Firebase sync. Only actual authentication success reported by OpenSSH updates it. A missing or damaged file falls back to normal host ordering without blocking connections.
- Connection audit Logs are sensitive usage history. They retain the interactive SSH connection's host name, platform, account endpoint, source-device snapshot, start/authentication/end times, and structured outcome, but receive no passwords, OTPs, private keys, commands, terminal input/output, or OpenSSH verbose debug output. Local directories/files use `0700`/`0600` permissions and atomic writes. Records are limited to 30 days and 5,000 entries and excluded from host exports. Logs are read-only, with no individual-delete or clear-all action; damaged files are isolated as backups.
- With sync enabled, only finalized Logs are end-to-end encrypted using the existing master key and AES-256-GCM, then stored in a dedicated Firestore collection under the current UID. Hosts, accounts, addresses, source devices, times, and outcomes are inside the ciphertext. Live status, running timers, and heartbeats are not uploaded. The fixed 30-day cleanup uses Firestore's server time to exclude expired local records before removing expired ciphertext, preventing offline devices from reviving old records.
- Sync execution diagnostics are separate, in channel-isolated `Sync Diagnostics/events.json`, with directory/file permissions of `0700`/`0600` and limits of 1 MiB/1,500 entries. Records older than seven days are removed on load and when adding events. Only times, random round IDs, enumerated triggers/stages, counts, allow-listed error categories, and numeric codes are stored. UIDs, hosts, accounts, IPs, device names, URLs, raw error text, request contents, and secrets are excluded. Diagnostics neither sync nor upload automatically; users must actively copy them to share. Failure to save diagnostics does not affect SSH or sync.
- Host-to-group dragging is enabled only in the visible All Hosts content area and tracks only mouse events in the current MyTerm window that originate on an existing host card. Monitoring stops when Terminal or another view covers the host page, a group is opened, or confirmation is pending. It accepts no drag payload from other apps and does not intercept dragging on other views. After the drop, the user must confirm before `HostStore` validates and saves the host/group change. Cancellation, invalid targets, and the existing group produce no inventory write.
- With password authentication, a saved password is filled automatically only at the first SSH `password:` prompt. A repeated login prompt does not resend the old value; the next manual entry becomes a replacement candidate awaiting verification. Later sudo or application prompts do not receive automatic login filling.
- When no vault password exists or the initial saved password is rejected, MyTerm temporarily tracks input only after an SSH login-password prompt. It offers to save or replace the password only after local `/usr/bin/ssh` reports `Authenticated ... using "password"` through its private `0600` diagnostic file. A repeated prompt clears the failed attempt before capturing the next entry.
- Forced password changes use a separate flow from the normal fill gate. An isolated `New password`, OTP, `sudo`, or confirmation prompt does not start capture. MyTerm offers to update the vault only after recognizing the current-password, new-password, and confirmation sequence, comparing the new entries in constant time, and observing an explicit success marker from the remote output. It never silently overwrites a saved password.
- Each interactive SSH session uses a short-lived `0600` OpenSSH diagnostic file to establish connection stages and password-authentication outcomes. Raw verbose lines may include hosts, accounts, fingerprints, algorithms, or local private-key paths. The UI receives only allow-listed structured summaries and useful non-debug OpenSSH errors. `debug1:`–`debug3:`, local configuration reads, SSH Agent sockets, and provider traces are excluded; complete local paths are redacted. Diagnostics are not synced, uploaded, or retained long-term. Temporary files are deleted after authentication, cancellation, failure, or session end.
- When a user copies connection diagnostics, the report includes the host endpoint, structured stages, failure category, recovery suggestions, and the same sanitized non-debug OpenSSH errors. It excludes verbose debug output, passwords, key contents, full local private-key/configuration paths, and SSH Agent sockets.
- Temporary passwords use mutable buffers that are overwritten and cleared on replacement, failed authentication, mismatched entries, declined saving, successful saving, cancellation, or session cleanup.
- Successful `keyboard-interactive` authentication does not prompt to save input because it may be an OTP or non-reusable challenge. A temporary username is not bound to the original host account's Keychain item.
- Saved passwords are used only when the session account matches the host's nonempty default username. Switching accounts temporarily does not expose another account's password.
- Manual Fill Password sends password bytes only to that tab's pseudo-terminal, then immediately clears the temporary mutable buffer.
- Local Terminal always launches `/bin/zsh`, with the shared SSH environment allow-list plus `SHELL=/bin/zsh`.
- Platform detection first examines bounded terminal output already displayed to the user. For an unknown platform, it may open a short-lived, noninteractive SSH connection to read `/etc/os-release`, compatible release files, and `uname -a`. It does not use `sudo`, write remotely, or put passwords in arguments or regular files. Failure or timeout leaves the generic icon.
- Serial accepts only existing `/dev/cu.*` or `/dev/tty.*` character devices. Options are passed as arguments to fixed `/bin/stty` and `/usr/bin/screen` executables without shell string interpolation.
- The version 0.1 data migration preserves host UUIDs and their Keychain associations, creating an owner-only backup before changing the format.
- The rename to MyTerm deliberately preserved the original Bundle ID, Keychain services, and Application Support directory so existing passwords remain associated with the same UUIDs.
- Password deletion removes the exact host entry from the vault and retains non-secret suppression markers for legacy Keychain items that could not yet be removed, preventing old passwords from returning. Legacy permission failures do not block host deletion.
- The schema 3 nested-group migration creates a `0600` backup first. Missing parents or cyclic relationships are repaired at the root level without deleting hosts or groups.
- `~/.ssh/known_hosts` is read only when the user chooses Load or Sync. Imported trust snapshots and display indexes are stored in separate owner-only files; no watcher or background sync is installed.
- MyTerm does not read, decrypt, or extract the Termius Vault database. The optional repository tool accepts compatible host/group metadata and converts fields locally through the installed Termius runtime. It has no code to read or output password, passphrase, token, or private-key fields. Termius internal formats may change; see [Termius migration](TERMIUS_MIGRATION.en.md) for the full limitations and procedure.
- MyTerm/Termius imports constrain file size and record counts, validate group hierarchies and fields, preview conflicts, allocate new host UUIDs, and create a `0600` inventory backup before applying data.
- Even without credentials, migration output in `Exports/` may disclose host names, IPs, accounts, and internal groups. The entire directory is Git-ignored, output files use `0600` permissions, and release safety checks reject private output not protected by exclusion rules.
- Custom import filters selected items before analyzing conflicts. It creates only the ancestor groups needed by accepted hosts; skipped or invalid data does not leave empty groups.
- MyTerm exports use an explicit field allow-list and exclude Keychain passwords, private-key contents, passphrases, tokens, and local private-key paths. Exported JSON is still plaintext and may contain host addresses, usernames, and notes; users must protect it.

## SSH trust

- Connections use the system `/usr/bin/ssh`; MyTerm does not implement the cryptographic protocol itself.
- Host keys are stored in an app-specific `known_hosts` file with `0600` permissions.
- `StrictHostKeyChecking=ask` requires confirmation for new hosts and blocks changed keys.
- System-default mode follows the current OpenSSH algorithm policy.
- RSA compatibility and custom algorithms apply only as arguments for the specific host connection. They do not modify `~/.ssh/config` or global policy.

## Known limitations

- Automatic filling applies only to the first password prompt in a session configured for password authentication. A malicious endpoint that has passed host-key verification remains within that connection's credential trust boundary.
- Manual filling cannot prove where a prompt originated. Use it only when you are certain you are connected to the correct host and the display is actually requesting a password.
- The app stores private-key paths as host settings but does not copy private-key contents.
- Logs cover only interactive SSH started from the host library. Local Terminal, SFTP, Serial, and activity before the feature was enabled do not generate or backfill audit records.
- Independent distributors are responsible for code signing and Apple notarization. Unnotarized builds transferred to another Mac may require user approval. Self-signed certificates have no Apple Team ID, so Keychain may regard builds as different identities. A single vault root key keeps update approvals from growing with host count; configured in-app updates must still pass separate Sparkle Ed25519 verification.
- In-app updates require an installation location where the app can be replaced. Sparkle safely stops when running from an archive, read-only image, App Translocation after download, or another temporary location. Place production `MyTerm.app` in Applications.
- `sudo` / `su` passwords are not submitted automatically. MyTerm enables the fill button or shortcut only at a recognized safe password prompt, keeping final confirmation with the user.
- Platform detection is conservative and best-effort. Without explicit operating-system or network-device markers, it keeps a generic icon.
- Serial connections may fail if an adapter disconnects, another process owns the port, or macOS/driver permissions block access. Full end-to-end validation with a physical USB Serial device has not yet been completed.
- Cross-device sync is optional and off by default. When enabled, hosts, groups, passwords, and finalized Logs reach Firebase only as individually end-to-end encrypted records. Master keys and decrypted passwords are stored only in each Mac's local encrypted vault, whose root key is a ThisDeviceOnly Keychain item. Private-key files/paths and known_hosts do not sync. See [System architecture](ARCHITECTURE.en.md). A self-hosted sync backend must deploy the repository's Security Rules, not unrestricted test rules; see [Firebase setup](FIREBASE_SETUP.en.md).
- Production, development, and update-lab Google refresh tokens reside in their own channel vaults. Only production may perform a one-time compatibility migration from early production Keychain items. Dev/Update Lab do not read old production sessions and perform one-time cleanup of tokens previously imported into their own vaults by mistake, without deleting the production session.
- Host/group deletions sync as authenticated, end-to-end encrypted tombstones. Applying remote deletions first backs up the local inventory. Removing a remote host then cleans its password from that Mac's vault; permission problems with legacy Keychain items do not block inventory deletion.
